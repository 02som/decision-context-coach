# Jira 이슈 전처리 규칙 및 구현

**관련 WBS ID:** 3.2

**담당자:** 박경서

**작성일:** 2026-11-25

**상태:** 구현 완료 (R6 기준 3,000자 실측 확정)

**관련 Jira 작업:** DFAS-152

## 1. 목적

DFAS-151에서 확정한 세 필드(`key`, `summary`, `description`)를 AI에 넣기 전에 다듬는 규칙을 정하고, 그 규칙대로 전처리 함수를 구현한다.

## 2. 요구사항 및 작업 범위

- API Contract v0.2.0(DFAS-124) 2절: ADF 설명을 **뜻을 유지하며(preserving meaning)** 일반 텍스트로 변환. 설명이 없으면 `""`, `key`·`summary`가 없으면 오류
- API Contract v0.2.0 4절: 평가에도 2절로 정규화한 같은 이슈를 넘긴다 → 이 규칙은 **분석과 평가 둘 다의 입력**이 된다
- 범위: 정규화 규칙 설계, 기존 백엔드 코드 변경
- 범위 밖: 필드 선택(DFAS-151), 테스트 이슈(DFAS-153), 프론트엔드 `extractJiraText`(Mock 분석 화면 표시용으로만 쓰임)

## 3. 상세 설계

### 3.1 필드별 정규화

| 필드 | 정규화 | 없을 때 |
|---|---|---|
| `key` | 그대로 | 오류 |
| `summary` | 앞뒤 공백 제거 | 오류 |
| `description` | 3.2·3.3 규칙 | `""` |

- 평가 경로는 `normalizeIssueContext`(`src/evaluation/validation.js`, MT2)가 `key`·`summary` 확인과 공백 정리를 이미 한다. 새 함수는 이와 중복하지 않고 `description` 변환을 맡는다

### 3.2 `description` 규칙 (R1~R5)

API Contract v0.2.0 2절은 ADF 설명을 "뜻을 유지하며" 일반 텍스트로 바꾸라고만 하고 방법은 정하지 않았다. 그래서 "뜻이 유지된다"를 다음 세 가지 기준으로 판단했다.

1. **문장이 온전해야 한다.** 분석 프롬프트가 "근거가 되는 Jira 문구를 인용"하도록 하므로, 문장이 쪼개지면 인용도 깨진다.
2. **글의 구조가 남아야 한다.** 문단·목록·표·코드가 사라지면 "목표와 완료 기준", "대안 목록", "비교표"처럼 내용끼리의 관계를 알 수 없다.
3. **내용을 더하거나 빼지 않는다.** 원문에 없는 내용을 넣거나 있는 내용을 지우면 뜻이 바뀐다.

| # | 규칙 | 근거 기준 | 이유 |
|---|---|---|---|
| R1 | 한 문단 안의 텍스트 조각은 줄바꿈 없이 이어 붙인다 | 1 | 굵게·링크 등으로 나뉜 조각이 문장을 쪼개지 않게 |
| R2 | 문단 사이는 빈 줄 하나 | 2 | "목표 / 완료 기준"처럼 덩어리 구분 유지 |
| R3 | 글머리 목록 `- `, 번호 목록 `1.` 유지, 하위 목록은 공백 2칸 들여쓰기 | 2 | 대안·완료 기준·순서가 목록으로 적히는 경우가 많음 |
| R4 | 제목: 텍스트만 한 줄 / 코드 블록: 내용 그대로, 앞뒤 ```` ``` ```` / 표: 한 행 한 줄, 칸 사이 ` \| ` / 링크: 링크 텍스트(없으면 주소) / 이미지·첨부: `[attachment]` | 2, 3 | 구조는 살리고, AI가 읽을 수 없는 것은 지우지 않고 존재만 표시 |
| R5 | 앞뒤 공백 제거, 연속 빈 줄은 하나로, 표 칸 앞뒤 공백 제거. 코드 블록 안은 제외 | 3 | 뜻에 영향 없는 공백만 정리. 공백만 있는 설명은 `""`. 토큰 절약. 표 칸 공백은 실제 이슈(DFAS-156)에서 발견 |

### 3.3 긴 설명 처리 (R6)

API Contract v0.2.0에는 긴 설명에 대한 내용이 없다. 설명이 너무 길면 Groq가 요청을 거절할 수 있는데, 기존 코드는 이유와 상관없이 "잠시 후 다시 시도해 주세요"를 보여 주므로 사용자는 계속 실패하고 이유를 모른다 (`src/analysis/groq-client.js`, `main` `f2cec8c`).

| # | 규칙 | 근거 기준 | 이유 |
|---|---|---|---|
| R6 | 설명이 3,000자를 넘으면 앞부분부터 남기고 자른 뒤, 끝에 `(Truncated: the description was too long, so only the first M of N characters are included.)`를 붙인다 | 1, 3 | 한도 안에서 앞부분이라도 분석한다. 잘린 사실을 숨기지 않아 AI가 뒷부분을 '확인 불가'(`Unknown`)로 다룰 수 있다 |

- 위치: `adfToPlainText`의 마지막 단계. 분석(`toJiraContext` 경유)과 평가(직접 호출)가 모두 이 함수를 거치므로 같은 기준이 적용된다 (MT2 요청)
- 문장 끝이나 줄바꿈에서 자른다 (기준 1). 최대 길이의 80% 뒤에서 찾지 못하면 최대 길이에서 자른다
- 코드 블록 중간에서 잘리면 ```` ``` ````로 닫는다
- 사용자 화면 안내는 이번 범위에서 제외 (팀장 확인 예정)
- AI에게 보내는 문구(잘림 안내, `[attachment]`)는 앱 영어화(main `923fb58`)에 맞춰 영어로 쓴다. 3,000자 실측은 한국어 출력 기준이며, 영어 출력은 토큰을 덜 쓸 가능성이 높아 기준을 유지한다 [추정]

**결정 과정**

- 처음 제안: 자르지 않고 "분석할 수 없다"고 안내 (내용 손실 없음). 실패 길이와 팀 플랜이 미확인이라 보류
- 팀장 결정 (2026-11-25, DFAS-152 댓글): 배포 앱도 무료 플랜. 분석·평가에 같은 기준을 적용하고, 토큰 한도를 고려해 자르되 잘린 사실을 확인할 수 있게. JSON 계약과 평가 모듈은 유지
- 앞부분부터 남기는 이유: Jira 설명은 배경·목적을 앞에 적는 경우가 많다 [추정]. 결정이 끝에 적힌 경우는 DFAS-153에서 확인

**3,000자 근거** (DFAS-153 실측, 2026-11-25)

DFAS-157(긴 테스트 이슈)을 길이별로 잘라 실제 앱과 같은 프롬프트·설정으로 Groq에 분석 → 평가를 요청하고, Groq가 돌려준 실제 토큰 수(`usage`)를 기록했다. 요청 사이는 65초를 두어 분당 한도가 서로 섞이지 않게 했다.

| 설명 길이 | 분석 총합 | 평가 입력 | 평가 총합 |
|---|---|---|---|
| 4,479자 (자르지 않음) | 4,895 | 측정 못 함 | 측정 못 함 |
| 4,000자 | 3,891~4,878 | 5,570 | 6,848 |
| 3,000자 | 3,976 | 4,927 | 6,016 |
| 2,000자 | 3,070~3,215 | 4,309 | 6,177 |

- 한글 1자 ≈ 0.58토큰 (분석 입력 토큰의 길이별 차이로 계산)
- 평가 요청이 가장 크다. 평가 입력은 프롬프트와 결정 카드가 대부분이라, 설명을 줄여도 크게 줄지 않는다
- 판단 기준: **평가 요청 하나가 응답 자리(`max_completion_tokens` 2,000)를 다 써도 8,000 안에 여유 있게 들어가는 길이**

| 길이 | 평가 입력 + 응답 자리 최대 | 8,000까지 여유 |
|---|---|---|
| 4,000자 | 5,570 + 2,000 = 7,570 | 약 430 |
| **3,000자** | 4,927 + 2,000 = 6,927 | **약 1,070** |
| 2,000자 | 4,309 + 2,000 = 6,309 | 약 1,690 |

- 3,000자: 4,000자는 여유가 거의 없고, 2,000자는 설명을 1,000자 더 잃는 데 비해 평가 입력이 약 600토큰만 준다
- 잘린 경우(4,000·3,000·2,000자) 모두 AI가 결정을 지어내지 않고 "기술 선택 상태: 확인 불가"로 표시했다 (안내 문장의 효과로 보이나, 안내 없이 비교하지는 않았다 [추정])
- 한계: 길이별 1~2회 측정. 결정 카드 길이에 따라 평가 입력이 달라진다
- 측정 중 오류: 1차(요청 사이 20초)에서는 앞 요청과 분당 한도를 나눠 써서 429가 3회 났다. 2차(65초)에서는 "JSON 생성 실패"(400)가 2회 났다 (전체 14회 중). 길이와의 관계는 확인하지 못했다. 앱 동작 관련 문제는 DFAS-154로 넘긴다

| 플랜 | 무료 (배포 앱, 로컬 테스트 키 모두) | 팀장·MT2 답변 (DFAS-152 댓글) | 2026-11-25 |

### 3.4 기존 코드 변경

**문제: 현재 백엔드 `extractText`는 규칙과 맞지 않는다** (설명용 예시, 실행 확인 `main` `f2cec8c`)

① Jira 화면에 보이는 설명

> 인증은 **OAuth**로 결정했다
> - 대안: 세션 로그인

② Jira가 저장하는 모양 (ADF): 굵은 글씨 때문에 첫 문장이 세 조각(`text`)으로 나뉘어 저장된다

```json
{"type":"doc","version":1,"content":[
  {"type":"paragraph","content":[
    {"type":"text","text":"인증은 "},
    {"type":"text","text":"OAuth","marks":[{"type":"strong"}]},
    {"type":"text","text":"로 결정했다"}]},
  {"type":"bulletList","content":[
    {"type":"listItem","content":[{"type":"paragraph","content":[{"type":"text","text":"대안: 세션 로그인"}]}]}]}]}
```

③ 일반 텍스트로 바꾼 결과

현재 `extractText`:

```text
인증은 
OAuth
로 결정했다
대안: 세션 로그인
```

규칙 적용 (구현 결과, 테스트로 확인):

```text
인증은 OAuth로 결정했다

- 대안: 세션 로그인
```

1. **문장이 쪼개진다.** 굵게 표시된 단어 앞뒤로 줄이 바뀌어 한 문장이 세 줄이 된다. AI가 이 문장을 근거로 인용하기 어렵다 (기준 1 위반 → R1)
2. **목록 표시와 문단 구분이 사라진다.** "대안: 세션 로그인"이 목록 항목인지 알 수 없다 (기준 2 위반 → R2·R3)

이 함수는 분석(`analyzeIssue`)과 평가용 조회(`loadIssueForEvaluation`)가 함께 쓰므로 두 곳 모두 이 텍스트를 입력으로 받는다 (`src/resolvers/jira-issue-panel.js`).

**문제: 분석 경로는 `key`·`summary`가 없을 때 멈추지 않는다** (코드 확인 `main` `f2cec8c`)

- API Contract v0.2.0 2절은 "`key`나 `summary`가 없으면 오류"로 정했다
- 평가 경로는 `normalizeIssueContext`(MT2)가 이를 확인해 멈춘다
- 분석 경로(`analyzeIssue`, MT1)는 요청한 이슈 번호가 있는지와 Jira 조회 성공 여부만 확인하고, **Jira에서 받은 결과의 `key`·`summary`는 확인하지 않은 채** AI에 보낸다 → 2절과 어긋난다. 제목이 비면 AI가 빈 재료로 Decision Card를 만들게 된다
- 다만 Jira에서 이슈 번호는 항상 있고 제목은 필수 칸이라, 실제로는 조회가 비정상일 때만 생긴다 [추정]

**구현** (브랜치 `feature/jira-preprocess`, 커밋 `f743dec` R1~R5, `a1f7055` R6)

- 새 파일 `src/resolvers/jira-description.js`: `adfToPlainText`(R1~R6), `toJiraContext`(2절 형식 + `key`·`summary` 확인), `DESCRIPTION_MAX_CHARS`(3,000). 백엔드 파일을 여러 사람이 고치고 있어 새 파일로 분리
- `jira-issue-panel.js`(팀장 파일): `import` 1줄, `extractText` 호출 2곳 교체, 안 쓰게 된 `extractText` 삭제만 (+5/-26). 분석은 `toJiraContext`, 평가용 조회는 `adfToPlainText`
- 평가 모듈(`src/evaluation/`)과 JSON 계약은 바꾸지 않는다. 평가 경로의 `key`·`summary` 확인은 `normalizeIssueContext`가 계속 맡는다 (MT2 확인)
