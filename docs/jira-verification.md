### 4.2 문제 사례

**① 분석에서 JSON 생성 실패 시 재시도 없이 실패** (담당: MT1)

- 현상: Groq가 `400 Failed to generate JSON`을 돌려주면 분석은 바로 "AI analysis request failed. Please try again later."를 보여 준다. 평가는 같은 오류를 형식 오류로 보고 1회 재시도한다 (`src/evaluation/evaluate-answer.js`)
- 근거: 스크립트 요청 14회 중 2회 발생 (분석 1, 평가 1). 코드 `src/analysis/groq-client.js`
- 재현: 실제 오류는 가끔 나서 앱에서 일부러 만들 수 없다. 코드로 재현 — `requestGroqAnalysis`에 400 `json_validate_failed`를 돌려주는 `fetchFn`을 넣으면 Groq를 1번만 부르고 위 오류를 낸다
- 영향: 사용자가 Analyze를 다시 눌러야 한다. 시연 중 흐름이 끊긴다
- 제안: 평가처럼 형식 오류(400)일 때만 1회 재시도. 조건: 한도 초과(429)는 재시도하지 않는다. 분석의 한 번 대기 시간은 20초라, 재시도하면 Forge 처리 시간 제한(평가 코드 주석 기준 25초)을 넘을 수 있어 대기 시간을 줄여야 한다 [추정: Forge 제한은 공식 문서로 확인하지 않음]

**② Jira Evidence에 원문 두 문장을 섞은 인용** (담당: MT1)

- 현상: AI 인용 "해시를 설명으로만 만들면 설명이 바뀌면 예전 결과를 쓰지 않는다"는 원문에 없다. 원문의 "해시를 설명으로만 만들면, 제목만 바뀐 경우에는 예전 결과를 그대로 쓰게 된다."(위험)와 "설명이 바뀌면 예전 결과를 쓰지 않는다는 요구사항은…"(확인 결과)을 이어 붙여, 위험이 정상 동작처럼 읽히게 뜻이 바뀌었다
- 근거: 스크립트 인용 10개 중 1개 (DFAS-157, 3,000자). 앱(2026-11-26) 인용은 모두 원문과 일치
- 재현: DFAS-157을 여러 번 분석하고 Jira Evidence의 따옴표 문장을 원문에서 찾는다. 가끔 생겨 재현 확률이 낮다
- 영향: 따옴표로 보여 주므로 사용자는 Jira에 실제로 적힌 문장으로 믿는다
- 제안: 화면에 보여 주기 전에 따옴표 안 문장이 설명에 그대로 있는지 코드로 확인하고, 없으면 따옴표를 빼거나 "(paraphrased)"를 붙인다

**③ "idk" 답변에 3점** (담당: MT2)

- 현상: "idk"는 3/12(정확성·근거·설명 각 1점), 의미 없는 글자("어엄", "asdf")는 0/12
- 근거: 팀장 실행(영어 버전 전)과 앱 실행(2026-11-26) 모두 "idk" 3/12
- 재현: DFAS-156 분석 → 답변 `idk` → 3/12 (2회 중 2회)
- 원인으로 보이는 것: `docs/evaluation-rubric.md`에 "질문에 답하지 않은 답변" 기준이 없다. 각 항목의 0점 기준(틀림·모순 / 무관한 일반론 / 결론만 있음) 어디에도 "모른다"가 맞지 않는다 [추정]
- 영향: 등급은 Insufficient로 맞지만, 답하지 않아도 점수를 받는다
- 제안: 기준표에 "질문에 답하지 않은 답변은 모든 항목 0점" 추가

**④ 설명이 잘리면, 잘린 부분과 맞는 답이 감점됨** (담당: MT3, 관련 MT2·MT1)

- 현상: DFAS-157의 실제 결정은 "후보 2(메모리 캐시)"로 3,000자 뒤에 있다. 답변 "I would use memory cache first."에 대해 평가가 "The claim that memory cache should be used first cannot be verified from the Jira issue."로 표시했다 (1/12)
- 원인: R6가 앞 3,000자만 남기고, 평가도 잘린 설명을 받는다. 잘림 안내 문장이 있어도 잘린 부분일 수 있는 주장을 "확인 불가"로 처리했다
- 재현: DFAS-157 분석 → 원문의 결정(메모리 캐시)을 언급하는 답변 → Unverified Claims에 표시 (1회)
- 영향: 사용자는 설명이 잘린 줄 모르므로 맞는 답이 왜 감점됐는지 알 수 없다. 설명이 3,000자를 넘고 결정이 뒤에 있을 때만 생긴다
- 제안 (마감 후 선택): A. R6에서 앞과 끝을 함께 남기기 (MT3) / B. 평가 프롬프트에 "설명이 잘렸으면 잘린 부분일 수 있는 주장은 감점하지 않음" (MT2) / C. 사용자 화면에 잘림 안내 (MT1). 지금 JSON 계약에는 잘렸는지 알려 줄 칸이 없어, 계약에 칸을 추가하거나 설명 끝의 "(Truncated" 문구를 화면에서 찾아야 한다

### 4.3 관찰한 특성

- 분당 토큰 한도: 스크립트로 분석 후 20초 만에 평가하면 429가 3회 났다 (2026-11-25, 한국어). 앱에서 분석 직후 약 10초 만에 평가해도 재현되지 않았다 (2026-11-26, 영어). 여러 사용자가 동시에 쓸 때는 확인하지 못했다
- 같은 이슈도 실행할 때마다 결정 문구, 인용, 질문이 달라진다
- 설명이 없는 이슈(DFAS-158)는 질문이 일반론으로 흐른다 ("오타 수정이 자동 문서 생성·배포에 영향이 없는지 어떻게 확인할까"). 없는 사실을 단정하지는 않았다
